# 0001. Формат описания стандарта данных расписания

**Статус:** предложено.

## Контекст

Orbit приводит расписания разных учебных заведений к одному открытому стандарту ([требования](../standard/requirements.md)). Стандарт нужен трём сторонам:

- **коннекторам**: они пишут данные и должны проверять, что выдают корректный результат;
- **приложению Orbit**: оно читает данные, в том числе офлайн на телефоне;
- **сторонним разработчикам**: они должны понять формат без чтения кода Orbit и использовать его на любом языке.

Отсюда требования к формату: описание отдельно от кода, машинная проверка, поддержка в основных языках, понятность человеку, версионирование.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **JSON + JSON Schema (2020-12)** | Стандарт IETF/де-факто; валидаторы и генераторы типов почти для любого языка; данные читаются глазами; браузер и PWA работают с JSON без библиотек | Схема многословна; нет встроенной бинарной компактности |
| Protocol Buffers | Компактно, быстро, строгие типы, генерация кода | Данные не читаются глазами; нужен компилятор схемы; для веб-клиента — лишняя библиотека; хуже подходит для «открытого формата для всех» |
| CSV-набор по образцу GTFS | Просто, открывается в Excel, проверенная идея (GTFS — стандарт транспортных расписаний) | Плохо выражает списки и вложенность (несколько преподавателей у пары); слабая типизация; проверка — самописная |
| iCalendar (RFC 5545) | Готовый стандарт, импорт в любой календарь | Нет понятий группы, подгруппы, аудитории, публикации; честность данных («не опубликовано» vs «пар нет») не выражается. Годится как *экспорт*, а не как основа |
| Только TypeScript-типы / код | Быстро для одного языка | Привязывает стандарт к реализации — противоречит принципу «стандарт отдельно от приложения» |

## Решение (предлагается)

1. **Данные — JSON (UTF-8). Схема — JSON Schema draft 2020-12.** Схема лежит в репозитории отдельно от кода приложения (например, `standard/schema/`) и является источником истины. Типы для языков генерируются из неё, а не наоборот.
2. **Семантическое версионирование стандарта.** Каждый документ содержит версию стандарта, по которой он записан. Мажорная версия меняется при несовместимых изменениях, минорная — при добавлении необязательных полей. Пока стандарт не стабилен — версии `0.x`, и в них допустимы несовместимые изменения.
3. **Строгость к своему, терпимость к расширениям.** Поля, описанные в стандарте, проверяются строго. Для данных источника, которым в стандарте ещё нет места, — отдельное явно названное поле расширений (например, `x-source`), а не произвольные поля где попало.
4. **Справочники и пары отдельно.** Документ публикации содержит справочники (корпуса, аудитории, группы, преподаватели, предметы) и пары, которые ссылаются на них по идентификаторам. Это убирает дублирование (в источнике каждая из 383 пар несёт полную копию корпуса, группы, предмета) и даёт устойчивые связи.
5. **Примеры и проверка — часть стандарта.** Рядом со схемой лежат корректные и заведомо некорректные примеры (с вымышленными данными); проверка всех примеров против схемы выполняется в CI.
6. **iCalendar — как формат экспорта** из приложения, а не как основа стандарта.

## Последствия

- Коннектор на любом языке проверяет свой результат готовым валидатором JSON Schema.
- Размер данных больше, чем у бинарного формата. Для офлайн-режима это решается сжатием при передаче (gzip/brotli) и тем, что справочники не дублируются.
- JSON Schema не выражает всех правил (например, «аудитория пары существует в справочнике»). Такие проверки придётся описать текстом в документации стандарта и реализовать в отдельном валидаторе.
- Выбор не фиксирует язык и фреймворк приложения или коннекторов — это отдельные решения.

## Что нужно, чтобы принять решение

- Согласие автора проекта с выбором JSON + JSON Schema.
- Ответы на открытые вопросы из [требований](../standard/requirements.md#открытые-вопросы), влияющие на структуру документа: единица публикации, термин для корпуса.
