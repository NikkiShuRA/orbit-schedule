# AGENTS.md

Инструкции для ИИ-агентов (Claude Code, Codex, Cursor и других), работающих с этим репозиторием.

## Проект

**Orbit · Орбита** — расписание колледжей и вузов в одном месте. Подробности для людей — в [README.md](README.md).

Архитектура в трёх частях:

1. **Открытый стандарт данных расписания** — схема, описанная отдельно от приложения; ею может пользоваться кто угодно.
2. **Коннекторы** — по одному на источник (JSON из 1С, xlsx, PDF-сканы и т. д.). Коннектор читает исходные данные и приводит их к стандарту. Ничего не додумывает.
3. **Приложение** — интерфейс для студентов и преподавателей: своя группа или свои пары при входе, текущая пара, свободные кабинеты, работа офлайн.

Предшественник — [«Мой Сиелом»](https://github.com/NikkiShuRA/my-sielom-web) (ванильный JS + HTML/CSS, PWA, `server.js` на Node). Его опыт можно изучать, но код оттуда не переносится автоматически.

## Текущий статус

**Ранняя разработка.** Стек и размещение выбраны в [ADR 0003](docs/decisions/0003-stack-and-hosting.md): коннекторы и серверная часть — **Go**, приложение — **TypeScript**, публикация — GitHub Actions + GitHub Pages, история данных в git.

Что уже есть:
- черновик 0.2 стандарта данных в `standard/` (JSON Schema, примеры, валидатор на Node.js) и такой же валидатор на Go;
- коннекторы СИЭУиП и СПК и CLI `orbit` (см. «Команды»). Основной адрес API СИЭУиП с ноября 2026 недоступен, данные идут с временного резервного зеркала ([#15](https://github.com/NikkiShuRA/orbit-schedule/issues/15)). У СПК время начала пар берётся с сайта расписания, у самих пар времени нет;
- публикация по расписанию: днём каждые 10 минут, ночью раз в час, в ветку `data` и на GitHub Pages ([ADR 0004](docs/decisions/0004-scheduled-publishing.md)); запускает её внешний таймер на Cloudflare Workers ([ADR 0011](docs/decisions/0011-external-trigger.md));
- нарезка для приложения: неделя каждой группы и преподавателя отдельным файлом и оглавление (`orbit slice`, [ADR 0006](docs/decisions/0006-coverage-and-slices.md)); всё это доступно как статичный API `api/v1` ([ADR 0008](docs/decisions/0008-versioned-data-api.md)) с описанием в OpenAPI 3.1 и схемами служебных файлов ([ADR 0009](docs/decisions/0009-api-description.md), [инструкция](docs/api.md)).

- приложение (`app/`, первая версия): поиск группы или преподавателя, неделя с текущей и следующей парой, работа без сети с честной пометкой о сохранённой копии и возрасте данных.

Чего ещё нет: нескольких расписаний сразу, свободных кабинетов и фоновой загрузки полных недель ([ADR 0007](docs/decisions/0007-full-weeks-and-several-schedules.md)) — они в issues. Решения для приложения приняты: офлайн — [ADR 0005](docs/decisions/0005-offline-storage.md), полные недели и несколько расписаний — [ADR 0007](docs/decisions/0007-full-weeks-and-several-schedules.md); фреймворк и инструменты — [ADR 0010](docs/decisions/0010-app-stack.md) (React, Vite, PWA на Workbox, Biome, Vitest). Что в работе и что дальше — на доске [Orbit](https://github.com/users/NikkiShuRA/projects/9) и в issues; что уже сделано — в [CHANGELOG.md](CHANGELOG.md).

Правила для кода:

- Коннектор — программа командной строки без зависимостей от GitHub; задачи GitHub Actions — тонкие обёртки над ней. Не нарушай правила переносимости из ADR 0003.
- Go-код пиши идиоматично и просто: сначала стандартная библиотека, минимум зависимостей.
- Фреймворки, библиотеки и структуру каталогов, которые не решены в ADR, не выбирай молча — предложи вариант с обоснованием и дождись решения.
- Когда появится новый код, дополни раздел «Команды».

## Команды

Стандарт (`standard/`, Node.js 22+):

```bash
cd standard
npm ci                                   # зависимости
npm test                                 # все примеры: valid/ проходят, invalid/ падают
npm run validate -- examples/valid/college-week.json   # проверить один документ
```

Приложение (`app/`, Node.js 22+, [ADR 0010](docs/decisions/0010-app-stack.md)):

```bash
cd app
npm ci                                   # зависимости
npm run dev                              # разработка: http://localhost:5173
npm run check                            # всё, что проверяет CI: типы, Biome, тесты, сборка, вес
npm run format                           # исправить форматирование и порядок импортов
npm run build && npm run preview         # собранное приложение с service worker: http://localhost:4173
```

Структура `app/src`: `api.ts` — типы читаемых файлов API и загрузка (ответ из кэша service worker помечен заголовком `x-orbit-from-cache`); `lib/` — логика без React (даты в часовом поясе учебного заведения, сборка недели из документа, раскладка дня и недели `calendar.ts`, поиск, выбор, возраст данных) с тестами `lib.test.ts`; `lib/browse.ts` — выбор по шагам (учебное заведение → корпус или отделение → курс → группа, буква → преподаватель); `lib/profile.ts` и `lib/store.ts` — профиль и настройки на устройстве (localStorage, только этот компьютер или телефон); `components/` — экраны (`Calendar.tsx` — виды «День» и «Неделя», `Finder.tsx` — боковая панель выбора и поиск, `Details.tsx` — подробности пары, `Me.tsx` — профиль и настройки; последние два грузятся при первом открытии), общие блоки (`ui.tsx`, в том числе панель `Sheet`) и значки (`Icon.tsx`, рисованные, без библиотеки); почему экран расписания устроен так — в [docs/app-design.md](docs/app-design.md), меняешь поведение экрана — правь и его; `hooks.ts` — загрузка файла и текущее время; `sw.ts` — service worker; `testdata.ts` — вымышленные данные для тестов; `assets/fonts/` — шрифты Wix Madefor Display и Inter (SIL OFL 1.1, тексты лицензий рядом). Логику пиши в `lib/` и проверяй тестами там, компоненты держи тонкими.

Данные при разработке берутся по адресу `./api/v1/` рядом с приложением; другой адрес — `VITE_DATA_URL=https://nikkishura.github.io/orbit-schedule/api/v1/ npm run dev`. Бюджет веса — 100 КБ сжатого JS при первом открытии (`npm run size` меряет основной файл; части, загружаемые позже через `lazy`, в него не входят); превышение — повод для обсуждения, а не для поднятия лимита.

Таймер публикации (`ops/trigger/`, Node.js 22+, без зависимостей, [ADR 0011](docs/decisions/0011-external-trigger.md)):

```bash
cd ops/trigger
npm test                                 # тесты воркера, без сети
npx --yes wrangler@4.155.0 deploy --dry-run --outdir "$(mktemp -d)"   # проверить настройки без выкладки и без входа
```

Выкладку (`wrangler deploy`) делает только владелец, по `ops/trigger/README.md`.

Коннекторы (Go 1.25+, модуль в корне репозитория):

```bash
gofmt -l .                                       # перед PR: должно быть пусто (код выхода всегда 0, смотри на вывод)
go vet ./...                                     # статический анализ
go test ./...                                    # все тесты, включая общие примеры стандарта
go run ./cmd/orbit fetch sieup --out data        # текущая неделя СИЭУиП → data/sieup/<понедельник>.json
go run ./cmd/orbit fetch sieup --out data --date 2026-11-09
go run ./cmd/orbit fetch sieup --out data --weeks 2   # эта и следующая недели; неизменившиеся файлы не перезаписываются
go run ./cmd/orbit fetch sieup --out data --base https://example.org/api   # свой адрес API вместо встроенных
go run ./cmd/orbit fetch spk --out data --weeks 2     # СПК → data/spk/<понедельник>.json (один --base, без зеркал)
go run ./cmd/orbit fetch spk --out data --site https://example.org   # свой адрес сайта, откуда берётся время начала пар
go run ./cmd/orbit validate data/sieup/*.json    # проверить документы
go run ./cmd/orbit slice --in data --out site    # нарезка для приложения: site/index.json, site/<источник>/catalog.json, groups/, teachers/
```

Коды выхода `orbit`: 0 — успех, 1 — ошибка, 2 — неверные аргументы, 3 — ни одна из запрошенных недель ещё не опубликована. После успешного `fetch` рядом с документами лежит `status.json` — когда источник проверяли и что вышло с каждой неделей.

Структура: `cmd/orbit` — CLI; `internal/standard` — типы документа и валидатор (схема + ссылки); `internal/sieup` — коннектор СИЭУиП; `internal/spk` — коннектор СПК (никогда не вызывает `update-schedule` у API: это меняет состояние источника); `cmd/orbit/sources.go` — список источников для `fetch`; `internal/slice` — нарезка недель на группы и преподавателей и оглавление; `standard/schema/embed.go` встраивает схему в Go; `api/v1` — описание API: `openapi.json` и `schemas/` (публикуются как есть) и пакет Go, который их встраивает и проверяет служебные файлы (`index.json`, `catalog.json`, `status.json`) перед записью.

Меняешь формат служебного файла — правь его схему в `api/v1/schemas/` и `openapi.json` в том же PR: тест сверяет поля в Go и в схемах. Внутри `v1` — только совместимые изменения ([ADR 0008](docs/decisions/0008-versioned-data-api.md)). Id источника не может быть `schemas`, `openapi` или `index`.

CI: `.github/workflows/standard.yml` (Node, `npm test`), `.github/workflows/go.yml` (gofmt, vet, тесты с `-race`, govulncheck), `.github/workflows/app.yml` (аудит зависимостей, попадающих к пользователям, типы, Biome, тесты, сборка, бюджет веса) и `.github/workflows/trigger.yml` (тесты таймера публикации).

Публикация ([ADR 0004](docs/decisions/0004-scheduled-publishing.md)): `.github/workflows/publish.yml` запускает `orbit fetch` для каждого источника (сбой одного не мешает публикации остальных, но задача в итоге падает), коммитит изменения в ветку `data`, нарезает данные для приложения (`orbit slice`, [ADR 0006](docs/decisions/0006-coverage-and-slices.md); нарезка не коммитится) и выкладывает всё на Pages как статичный API (`https://nikkishura.github.io/orbit-schedule/api/v1/`, [ADR 0008](docs/decisions/0008-versioned-data-api.md)). Несовместимое изменение раскладки или служебных файлов — только новой версией рядом со старой, не правкой `v1`. Публикует только `main`; из других веток — пробный запуск. Ветку `data` руками не правь.

Своего расписания у `publish.yml` нет: GitHub выполнял его с опозданием на часы. Его запускает через `workflow_dispatch` воркер Cloudflare из `ops/trigger/` — днём каждые 10 минут, ночью раз в час ([ADR 0011](docs/decisions/0011-external-trigger.md)). Расписание воркера — в `ops/trigger/wrangler.toml`; меняется только через ADR. Выкладывает воркер владелец (`ops/trigger/README.md`): ни у агентов, ни у CI нет доступа к Cloudflare и токена. `.github/workflows/freshness.yml` раз в день проверяет `status.json` на сайте и падает, если источник не проверяли дольше 2 часов. Не возвращай расписание в `publish.yml`: два таймера опрашивали бы источники вдвое чаще.

## Работа с источниками

Серверы учебных заведений — чужие и часто слабые. Мы для них бесплатный гость.

- **Только чтение.** Не вызывай запросы, которые меняют состояние источника, даже если они открыты без авторизации (у СПК это `update-schedule`).
- **Представляйся.** Каждый запрос несёт User-Agent проекта (`OrbitSchedule (+https://github.com/NikkiShuRA/orbit-schedule)`); никаких личных адресов почты в нём.
- **По очереди, а не параллельно.** Запросы к одному источнику — последовательно, с таймаутами на соединение.
- **Частота — только через ADR.** Расписание запусков записано в [ADR 0004](docs/decisions/0004-scheduled-publishing.md); не поднимай его без решения.
- **Тесты не ходят в сеть.** Источник в тестах — `httptest` с вымышленными фикстурами из `testdata/`; адреса подменяются (`--base`, `--site`, поля клиента). Живой прогон на настоящем источнике — вручную, перед PR, и его итог (сколько пар, прошёл ли валидатор) пишется в описание PR. Выгрузки живых данных в репозиторий не коммить.
- **Сначала смотри на данные.** Перед тем как писать или менять коннектор, изучи настоящие ответы источника и запиши странности в [требования](docs/standard/requirements.md). Неясное — в issue с меткой `question`, а не догадка в коде.

## Новый источник

1. Issue с метками `connector` и `source:<id>` (новую метку источника создай). Изучи источник и дополни [требования](docs/standard/requirements.md).
2. Пакет `internal/<id>` по образцу `internal/sieup` или `internal/spk`: `api.go` — типы ответа источника, `client.go` — HTTP-клиент, `connector.go` — `Fetch` и чистая функция `convert`, `ErrNotPublished` для «неделя ещё не опубликована». Документ — одна неделя с понедельника; охват — то, что реально опубликовано.
3. Тесты в пакете на вымышленных фикстурах: правильный документ, странности источника, «не опубликовано», ошибки источника.
4. Регистрация в `cmd/orbit/sources.go` и тест CLI в `cmd/orbit/main_test.go` с поддельным сервером. Id источника — строчные латинские буквы, цифры и дефис; он становится частью адреса API и не может быть `schemas`, `openapi` или `index` (это проверяет тест).
5. Шаг в `.github/workflows/publish.yml` по образцу соседних: свой `id`, `continue-on-error: true`, код выхода 3 — не ошибка; добавь шаг в условие «Fail if a source failed».
6. Живой прогон и `orbit validate`, затем «Команды» здесь, README и CHANGELOG.

## Принципы, которые нельзя нарушать

- **Честность данных.** Показываем ровно то, что опубликовало учебное заведение. Никаких догадок, «исправлений» и заполнения пропусков. Если данные взяты из кэша на устройстве — явно сообщаем, что они могли устареть. Коннектор, который не смог разобрать фрагмент, сообщает об этом, а не угадывает.
- **Стандарт отделён от приложения.** Схема данных не зависит от деталей UI или конкретного коннектора. Изменения схемы — осознанные, с версионированием и описанием в документации.
- **Независимость.** Проект некоммерческий и не связан ни с одним учебным заведением. Не используй логотипы, фирменный стиль и формулировки, создающие впечатление официальности.
- **Лицензия AGPL-3.0-or-later.** Не добавляй зависимости и код с несовместимыми лицензиями (проприетарные, SSPL и т. п.); при сомнениях — спроси.
  Каждый файл с кодом (Go, JS/TS, скрипты) начинается с двух строк SPDX в синтаксисе комментариев языка, после shebang, если он есть:
  `SPDX-FileCopyrightText: 2026 Orbit contributors <https://github.com/NikkiShuRA/orbit-schedule>` и `SPDX-License-Identifier: AGPL-3.0-or-later`. Файлы данных (JSON, схема, примеры) покрывает `LICENSE`.
- **Репозиторий публичный.** Ничего лишнего в коммитах: никаких токенов, паролей, `.env`, личных адресов почты, локальных путей, имён компьютеров и пользователей ОС, логов и выгрузок с личными данными. Для тестов — вымышленные или публично опубликованные данные. Расписание преподавателей содержит ФИО — это публичные данные учебного заведения, но не собирай и не храни сверх необходимого.

## Документация и решения

- **Журнал изменений** — [CHANGELOG.md](CHANGELOG.md). Каждый PR с изменением, заметным пользователю или разработчику, добавляет строку в раздел «Не выпущено» — простым языком, что появилось или изменилось, со ссылкой на PR. Свежее — сверху; подразделы в порядке Keep a Changelog: «Добавлено», «Изменено», «Устарело», «Удалено», «Исправлено», «Безопасность».
- **Задачи** — в GitHub Issues, с метками (см. ниже). Новую работу сначала оформи как issue; PR закрывает его строкой `Closes #N`. Ход работы виден на доске GitHub Projects «Orbit», и её нужно вести:
  - взял задачу — её карточка в «In progress», задача назначена на исполнителя;
  - открыл PR — карточки PR и задачи в «In review». Новые PR попадают на доску сами, но в «Backlog»: перенеси их. PR, открытый не в `main` (поверх другого PR), GitHub с задачей не связывает, пока тот не перенацелится на `main`;
  - после слияния карточки должны уйти в «Done» сами, но это срабатывает не всегда: проверь и переведи вручную.
  - Метки: область (`standard`, `connector`, `app`, `infra`), источник (`source:…`), тип (`enhancement`, `bug`, `question`, `documentation`), `blocked` — ждёт чего-то вне задачи. Dependabot ставит свои (`dependencies`, `github_actions`).
- Проектные решения фиксируй в `docs/decisions/` как короткие ADR (см. [шаблон](docs/decisions/README.md)), чтобы следующий агент не переоткрывал уже принятые вопросы.
  - Принятый ADR не переписывай задним числом. Новое решение — новый ADR со ссылкой «дополняет» или «заменяет», а у старого в статусе — ссылка на новый.
  - Мелкий параметр решения (например, частоту запусков) можно поправить на месте, если рядом написано, что было раньше и почему изменилось, со ссылкой на задачу.
- Стандарт данных — в `docs/standard/`. Начни с [требований](docs/standard/requirements.md): там перечислены реальные странности источников, которые стандарт обязан выразить. Пример из источника перед изменением схемы важнее догадок.

## Стиль работы

- Язык общения и документации — **русский**. Идентификаторы и комментарии в коде — на английском.
- **Сообщения коммитов, названия веток, заголовки и описания PR — на английском.** Формат коммита: заголовок до ~72 символов в повелительном наклонении (`Add schedule schema draft`), пустая строка, затем тело — что и зачем изменено.
- Коммиты маленькие и осмысленные. Ветка по умолчанию — `main`, работа идёт в отдельных ветках через PR.
- Автор коммитов — адрес GitHub вида `…@users.noreply.github.com`, не личная почта.
- **Слияние PR и удаление веток — только с явного согласия человека**, каждый раз отдельно. Это касается и PR от Dependabot: обновление зависимостей проверяет человек.
- `main` защищена правилами репозитория (ruleset «Protect main»): изменения только через PR, слияние только squash (заголовок коммита = заголовок PR), обязательны зелёные проверки `test`, `vulncheck`, `validate`, `app` и актуальность ветки относительно `main`; force push и удаление `main` запрещены. Не пытайся обойти эти правила; если они мешают — скажи человеку.
- Обязательные проверки запускаются на каждом PR, поэтому у `pull_request` в их workflow не должно быть фильтра `paths`, иначе PR без подходящих файлов зависнет навсегда.
- Тексты для пользователей — простым языком, без канцелярита.
- Скрипты и инструкции должны работать и на Windows, и на Unix. Окончания строк — LF (см. `.gitattributes`).
