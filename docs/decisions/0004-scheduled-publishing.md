# 0004. Публикация по расписанию: ветка `data`, коммит только при изменениях, статус проверки отдельно

**Статус:** принято 2026-11-08. Адрес данных уточнён [ADR 0008](0008-versioned-data-api.md); запуск по расписанию заменён внешним таймером в [ADR 0011](0011-external-trigger.md).

## Контекст

[ADR 0003](0003-stack-and-hosting.md) решил, что коннекторы запускает GitHub Actions по расписанию, результат публикуется на GitHub Pages, а история данных хранится в git. Где именно хранить историю — в ветке или в отдельном репозитории, — оставили до реализации ([#8](https://github.com/NikkiShuRA/orbit-schedule/issues/8)).

Ещё два вопроса возникли при реализации:

- В документе есть время получения (`provenance.retrievedAt`). Если перезаписывать файл при каждом запуске, каждый запуск будет коммитом, даже если расписание не менялось.
- GitHub отключает задачи по расписанию в репозитории без активности за 60 дней. Летом расписание не меняется дольше.

## Решение

1. **История — в ветке `data` этого же репозитория,** без общей истории с `main`.

   | | Ветка `data` | Отдельный репозиторий |
   |---|---|---|
   | Запись | встроенный токен задачи | нужен отдельный ключ — лишний секрет |
   | Pages | приложение и данные на одном сайте | два сайта |
   | Минус | `git clone` скачивает и историю данных (решается `--single-branch`) | второй репозиторий в обслуживании |

   Ветку `data` защищает набор правил: её нельзя удалить и переписать.

2. **Коммит — только при настоящем изменении.** `orbit fetch` не перезаписывает файл, если новый документ отличается от него только `retrievedAt`. Поэтому `retrievedAt` — время, когда это содержимое было получено впервые. История ветки — это история изменений расписания.

3. **Время последней проверки — в `<источник>/status.json`.** Его пишет `orbit fetch` после успешного запуска: когда проверяли и что вышло с каждой неделей (`updated`, `unchanged`, `not-published`). Неудачный запуск статус не пишет, чтобы не выглядеть свежей проверкой. В ветку `data` файл не коммитится (`.gitignore`), а выкладывается на Pages при каждом запуске. Это служебный файл публикации, а не часть стандарта; его формат может измениться вместе с [#9](https://github.com/NikkiShuRA/orbit-schedule/issues/9).

4. **Запуск каждые 10 минут днём и раз в час ночью.** С 7:00 до 21:00 по Сургуту — каждые 10 минут (в :03, :13, …), ночью — в 17 минут каждого часа. Минуты сдвинуты с начала часа: в это время очередь cron у GitHub самая загруженная. Сначала запуск был раз в час; днём это оказалось долго для замен, поэтому частоту подняли ([#26](https://github.com/NikkiShuRA/orbit-schedule/issues/26)). Чаще 10 минут не запускаем: у GitHub минимум 5 минут, на нём запуски сильнее всего опаздывают, а нагрузка на источники удваивается. При каждом запуске скачиваются текущая и следующая недели (`--weeks 2`), чтобы следующая неделя появлялась, как только её выложат. Код 3 («ничего не опубликовано») — не ошибка. Если источник не ответил, его данные не обновляются и на Pages остаются последние, а остальные источники публикуются как обычно; задача в конце помечается упавшей, чтобы сбой был виден (так с [#23](https://github.com/NikkiShuRA/orbit-schedule/pull/23)).

5. **Публикует только `main`.** Запуски из других веток и PR — пробные: скачивают и проверяют, но ничего не коммитят и не публикуют. Это же обеспечивает среда `github-pages`: развёртывание разрешено только из `main`.

6. **Против отключения через 60 дней** раз в неделю отдельная задача заново включает workflow через API GitHub. Коммитов-заглушек и сторонних action не нужно.

7. **Сайт:** данные лежат по адресу `https://nikkishura.github.io/orbit-schedule/data/<источник>/<понедельник>.json`. Корень сайта займёт приложение. С [ADR 0008](0008-versioned-data-api.md) адрес — `…/orbit-schedule/api/v1/<источник>/<понедельник>.json` (раньше был `…/data/…`): в адресе появилась версия.

## Последствия

- Задача остаётся тонкой обёрткой: перенести публикацию на свой сервер — значит запускать `orbit fetch --weeks 2` по cron в каталог с git и раздавать его веб-сервером.
- Время в документе — когда содержимое появилось, а не когда его проверяли. Приложение должно брать возраст данных из `status.json`, а `retrievedAt` — как время последнего изменения.
- Каждый запуск разворачивает Pages заново, даже без изменений, — чтобы обновить `status.json`. Это укладывается в лимиты GitHub.
- То, что включение workflow через API сбрасывает 60-дневный счётчик, — поведение GitHub, а не документированная гарантия. Если задача всё же отключится, GitHub пришлёт письмо; включить её можно вручную.
