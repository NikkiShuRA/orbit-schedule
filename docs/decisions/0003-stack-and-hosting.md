# 0003. Языки и размещение: коннекторы на Go, приложение на TypeScript, публикация без своего сервера

**Статус:** принято 2026-11-08. Инструменты приложения выбраны в [ADR 0010](0010-app-stack.md).

## Контекст

Стандарт 0.1 готов. Дальше нужны коннекторы (забрать расписание у учебного заведения и перевести в стандарт) и приложение. Проект некоммерческий, его ведёт один человек, поэтому важны стоимость, простота обслуживания и возможность переехать, если что-то не сработает.

Источники, разобранные к этому моменту (СИЭУиП, СПК), — JSON API. Оба рабочих адреса разрешают обращение из браузера (CORS), основной адрес СИЭУиП (`sielom.ru`) периодически не отвечает. В будущем ожидаются xlsx и PDF.

### Где запускать коннекторы

| Вариант | Плюсы | Минусы |
|---|---|---|
| **GitHub Actions по расписанию + GitHub Pages** | Бесплатно, нечего обслуживать, файлы легко хранить офлайн; Pages открывается из России (проверено «Мой Сиелом») | Задержка до следующего запуска (не чаще раза в 5 минут, бывают опоздания); серверы GitHub за границей, российский сайт может их не пускать; задачи по расписанию отключаются после 60 дней без коммитов |
| Коннекторы в браузере | Сервера нет, данные свежие | Зависит от CORS каждого источника; когда источник лежит, данных нет |
| Свой сервер (VPS) | Свежие данные, уведомления, российский IP | Деньги, обновления, безопасность, мониторинг |

### На чём писать коннекторы

| Язык | Плюсы | Минусы |
|---|---|---|
| **Go** | Один исполняемый файл без зависимостей; HTTP, JSON и параллельность в стандартной библиотеке; сильный выбор для будущего сервера; автор хочет его изучить | Слабее с PDF; в браузере практически не запускается |
| TypeScript | Один язык с приложением; может работать и в браузере | Для PDF и Excel слабее Python; для сервера — Node.js со своими зависимостями |
| Python | Лучший для PDF, Excel, скрейпинга | Два языка в проекте; не работает в браузере |

## Решение

1. **Коннекторы и серверная часть — Go.** Приложение — TypeScript. Граница между ними — стандарт данных: коннектор пишет JSON, приложение его читает. Валидатор стандарта в `standard/` остаётся на Node.js как инструмент самого стандарта; в коннекторах — своя проверка по той же JSON Schema.
2. **Публикация без своего сервера:** GitHub Actions по расписанию запускает коннекторы, результат публикуется на GitHub Pages вместе с приложением.
3. **История данных в git.** Каждая успешная публикация коммитится в отдельное хранилище данных (ветка или репозиторий — решим при реализации). Это даёт историю изменений расписания (основа для показа замен как разницы между версиями, а не догадки) и не даёт GitHub отключить задачи по расписанию.
4. **Переносимость — обязательное свойство:**
   - коннектор — программа командной строки (`orbit fetch <источник> --out <папка>`) без зависимостей от GitHub;
   - задача в GitHub Actions — тонкая обёртка над этой командой, без собственной логики;
   - результат — обычные файлы, без базы данных; их можно раздать любым веб-сервером;
   - адрес данных в приложении — настройка, а не константа в коде.
5. **Если источник не пускает серверы GitHub** — только для него данные забираются с российского VPS или компьютера автора тем же коннектором, публикация остаётся на Pages.
6. **Python — точечно,** только если встретится источник (например, сложный PDF), с которым Go не справляется.

## Последствия

- Затраты на размещение — ноль, пока хватает лимитов GitHub.
- Свежесть данных ограничена расписанием запусков; приложение обязано показывать возраст данных (`provenance.retrievedAt`).
- Переезд на VPS — смена места запуска и адреса данных, без переписывания кода.
- В проекте два языка. Обязательное правило против расхождения — общий стандарт и его примеры: коннекторы на Go проверяются теми же примерами из `standard/examples/`.
- Первым шагом нужно проверить, доступны ли источники с серверов GitHub (`.github/workflows/source-probe.yml`).
