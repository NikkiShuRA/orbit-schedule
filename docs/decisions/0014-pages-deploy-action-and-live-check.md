# 0014. Выкладка — снова `actions/deploy-pages`, а живой сайт проверяется после неё

**Статус:** принято 2026-11-15. Заменяет [ADR 0013](0013-pages-deploy.md).

## Контекст

По [ADR 0013](0013-pages-deploy.md) выкладку делал свой шаг: те же запросы, что у `actions/deploy-pages`, но с именем выкладки `<коммит>-<id запуска>-<попытка>`. Первый же запуск из `main` ([43710299512](https://github.com/NikkiShuRA/orbit-schedule/actions/runs/43710299512)) упал: на `POST /repos/{owner}/{repo}/pages/deployments` Pages ответил 404. Скорее всего, в `pages_build_version` Pages ждёт настоящий коммит репозитория. В документации этого нет, и в чужих отчётах этот путь тоже не был проверен ([#55](https://github.com/NikkiShuRA/orbit-schedule/issues/55)). Публикация из-за этого остановилась совсем.

## Решение

1. **Выкладку снова делает `actions/deploy-pages@v5`.** Других способов выложить сайт в Pages из workflow нет, а уникальное имя выкладки GitHub не принимает.
2. **Проверку живого сайта из ADR 0013 оставляем.** Метка `deploy.txt` (`<коммит> <id запуска> <попытка>`) кладётся в корень сайта, после выкладки шаг до 5 минут читает её с сайта, каждый раз с новым query string. Если сайт так и не отдал метку этого запуска, задача падает и прямо пишет, что данные на сайте устарели.

## Последствия

- Ответ действия «успешно» по-прежнему может относиться к старой выкладке того же коммита, но теперь зависание видно в том же запуске, а не через сутки.
- Само зависание проверка не лечит. Однажды помог новый коммит в `main` ([#55](https://github.com/NikkiShuRA/orbit-schedule/issues/55)). Если зависания повторятся, нужно отдельное решение: например, дать каждой выкладке настоящий новый коммит.
- Пока зависание не прошло, каждый запуск будет падать и присылать письмо. Это осознанно: устаревшие данные на сайте — настоящая поломка, а не шум.
