# 0011. Публикацию запускает внешний таймер на Cloudflare Workers

**Статус:** принято 2026-11-08. Дополняет [ADR 0004](0004-scheduled-publishing.md): меняет то, кто запускает публикацию, но не её частоту.

## Контекст

По [ADR 0004](0004-scheduled-publishing.md) публикацию запускает расписание GitHub Actions: днём каждые 10 минут, ночью раз в час. На деле GitHub выполняет его очень неточно ([#41](https://github.com/NikkiShuRA/orbit-schedule/issues/41)):

- первые ~10 часов после включения не было ни одного запуска по расписанию — ни с почасовым cron, ни с 10-минутным;
- после первого запуска следующего не было полтора часа вместо девяти.

GitHub прямо пишет, что запуски по расписанию могут задерживаться и пропускаться при нагрузке. Для расписания пар задержка на часы — это устаревшие замены.

Варианты:

| | Плюсы | Минусы |
|---|---|---|
| Оставить cron GitHub | ничего не делать, без секретов | запуски опаздывают на часы и пропадают |
| **Cloudflare Workers, Cron Triggers** | точный таймер, бесплатно с запасом, токен хранится зашифрованным, код и расписание — в репозитории | нужен аккаунт Cloudflare и токен GitHub |
| cron-job.org | настройка в веб-форме, без кода | настройки живут только в чужом аккаунте, их не видно в ревью; токен у небольшого стороннего сервиса |
| Свой сервер с cron | полный контроль | сервер нужно содержать |

## Решение

1. **Таймер — Cloudflare Workers.** Воркер в `ops/trigger/` по расписанию вызывает `workflow_dispatch` у `publish.yml` на ветке `main`. Больше он ничего не делает: скачивание, проверка, коммит в `data` и публикация остаются в GitHub Actions, как в ADR 0004.
2. **Расписание — в `ops/trigger/wrangler.toml`,** то же, что было в ADR 0004: днём (7:00–21:00 по Сургуту) в :03, :13, …, ночью в :17 каждого часа. Время в UTC. Менять частоту — по-прежнему только через ADR.
3. **Расписания в `publish.yml` нет.** Два таймера опрашивали бы источники вдвое чаще. Задача keepalive из ADR 0004 (пункт 6) больше не нужна: GitHub отключает только workflow с расписанием.
4. **Токен** — fine-grained personal access token владельца: доступ только к этому репозиторию, одно разрешение `Actions: Read and write`, срок — не больше года. Хранится только в секрете воркера (`GITHUB_TOKEN`), в репозиторий и CI не попадает. С ним можно запускать и отменять задачи Actions, но нельзя читать или менять код и данные.
5. **У воркера нет адреса в интернете** (`workers_dev = false`): запустить его может только таймер.
6. **Проверка свежести.** Отдельный workflow `freshness.yml` раз в день читает `status.json` каждого источника на сайте. Если последняя проверка источника старше 2 часов, задача падает, и GitHub пишет владельцу. Так видно, что таймер остановился, токен истёк или публикация ломается. Это единственное расписание в GitHub; опоздание на часы ему не страшно. Его, как прежде keepalive, держит включённым вызов API в самой задаче.
7. **Воркер написан на JavaScript без зависимостей,** тестируется встроенным `node --test`. `wrangler` нужен только для выкладки и запускается через `npx` с точной версией.

## Последствия

- Обновление снова регулярное; источники опрашиваются с той же частотой.
- Появился секрет вне GitHub и внешний сервис, от которого зависит публикация. Если Cloudflare недоступен, данные перестают обновляться, но сайт и последние данные остаются; через сутки это заметит проверка свежести. Опубликовать вручную можно в любой момент: Actions → Publish → Run workflow.
- Раз в год токен нужно перевыпустить и положить в воркер заново (`wrangler secret put GITHUB_TOKEN`). Если забыть, сработает проверка свежести.
- Выкладывает воркер владелец со своего компьютера (`wrangler deploy`); изменения кода и расписания воркера проходят через PR, как всё остальное.
- Переносимость по [ADR 0003](0003-stack-and-hosting.md) не страдает: воркер — тонкий таймер, его можно заменить любым cron, который умеет отправить один HTTP-запрос.
