# 0013. Своя выкладка на Pages с номером на каждый запуск и проверка живого сайта

**Статус:** принято 2026-11-15. Дополняет [ADR 0004](0004-scheduled-publishing.md) (выкладка на Pages при каждом запуске).

## Контекст

15 ноября 2026 с 09:34 UTC сайт перестал меняться, хотя каждый запуск публикации выкладывал свежие файлы и `actions/deploy-pages` отвечал «Reported success!» ([#55](https://github.com/NikkiShuRA/orbit-schedule/issues/55)). Проверено: в выкладке лежал свежий `spk/status.json`, а все четыре сервера Pages отдавали старый, так что дело было не в кэше. Сбоев на githubstatus.com не было. У других проектов в эти же недели было то же самое ([performanceinsights-ai/status#6](https://github.com/performanceinsights-ai/status/issues/6), [NormB/sipnab#739](https://github.com/NormB/sipnab/pull/739)).

Почему действие этого не заметило, видно из его кода (v5). Выкладку оно называет `pages_build_version = GITHUB_SHA`, и статус спрашивает по этому же имени. `main` меняется редко, а публикация идёт около 100 раз в день, поэтому все выкладки с 10 ноября назывались `c628fab`. Действие спрашивало статус самой первой из них, давно успешной, и через 4 секунды отвечало «успешно», что бы ни стало с новой. Почему GitHub перестал выкладывать новые версии, неизвестно. Изменить имя у действия нельзя: входа для этого нет, а переопределить `GITHUB_SHA` в шаге не даёт сам runner.

Варианты:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Оставить действие, проверять живой сайт | меньше своего кода | зависание видно, но не лечится; статус действия по-прежнему ничего не значит |
| Действие, а при зависании — повтор своим скриптом | обычно путь готовый | запасной путь срабатывает редко, и его поломку легко не заметить |
| **Свой шаг всегда** | у каждой выкладки своё имя, статус — именно её; путь проверяется каждые 10 минут | около 30 строк своего кода вместо готового действия |

## Решение

1. **Выкладку делает свой шаг в `publish.yml`** теми же тремя запросами, что и действие: токен OIDC запуска, `POST /repos/{owner}/{repo}/pages/deployments` и опрос статуса этой выкладки. Имя выкладки — `<коммит>-<id запуска>-<попытка>`, у каждого запуска своё.
2. **Метка запуска.** При сборке сайта в корень кладётся `deploy.txt` с теми же тремя значениями. Это не часть API `v1` ([ADR 0008](0008-versioned-data-api.md)), и в `openapi.json` её нет.
3. **Проверка живого сайта.** После выкладки шаг до 5 минут читает `deploy.txt` с сайта, каждый раз с новым query string, чтобы не попасть в кэш. Если сайт так и не отдал метку этого запуска, задача падает и прямо пишет, что данные на сайте устарели.

## Последствия

- Ответ «выложено» теперь относится к этой выкладке, а не к первой с тем же коммитом. Если GitHub всё равно не обновит сайт, это видно в том же запуске, а не только через сутки по проверке свежести.
- Если GitHub поменяет API выкладки Pages, шаг придётся править самим, а не обновлять версию действия. Dependabot об этом не скажет.
- Отмена запуска не отменяет уже созданную выкладку, как это делало действие. Новая выкладка через 10 минут всё равно её заменит.
